# Glossary

Terms used across AssetLite's documentation: plain English first, precisely second.

| Term | In plain English | Precisely |
|---|---|---|
| Asset lifecycle | The journey a piece of equipment takes: bought and shelved, handed to a person, sent for repair, taken out of service, finally disposed of. The system only offers sensible next steps, so a disposed laptop can never quietly be handed out again. | The `AssetStatus` state machine on the `Asset` aggregate: InStock, Assigned, Maintenance, Retired, Disposed. Transitions (`AssignTo`, `ReturnToStock`, `StartMaintenance`, `ResumeFromMaintenance`, `Retire`, `Dispose`, `TransferTo`) are legal only from defined states; illegal attempts return typed errors such as `Asset.CannotAssignRetired` that surface unchanged in the UI. |
| Organization hierarchy (HQ / region / site) | How the company is laid out for tracking: one headquarters at the top, regions under it, sites under those, rooms one level deeper. Equipment filed under a site automatically counts toward its region's and HQ's totals. | The `Office` tree governed by the `IOfficeHierarchy` domain service: a single root, maximum depth of four (HQ, region, site, room), no cycles, and no office may move under its own descendant; violations return typed office errors. |
| Asset tag | The human-friendly ID printed on each asset, in the shape `AST-000123`. Type it into search and that asset appears; the same tag rides on the label's barcode. | The `AssetTag` value object with its own parsing and formatting rules; the public identifier used in asset URLs and encoded into the generated label. |
| Barcode vs QR | Two kinds of scannable picture on the same printed label. The striped barcode is what a handheld scanner reads; the square QR grid is what a phone camera reads, and scanning it opens that asset's page. | The label pairs a Code 128 barcode (hand-rolled SVG encoder, verified against a computed known vector, zero barcode packages) over the asset tag with a QR code (QRCoder) encoding the public asset URL. |
| Asset register | The master list of everything the organization owns: tags, serials, offices, states, values. What an auditor or finance asks for, and what the Excel and PDF exports produce. | The full asset list served by the report queries; Excel (ClosedXML, styled totals) and PDF (QuestPDF, landscape, page numbers) exports are generated server-side from the same queries the UI reads (R6). |
| Assignment history / offboarding | Every hand-out and hand-back is kept as a dated record with the person's name. When someone leaves, their open assignment shows exactly what they still hold; recording a return never erases the past. | `Assignment` records (assignee name and email, assigned and returned timestamps) are part of the `Asset` aggregate; `AssignTo` opens a record, `ReturnToStock` and `TransferTo` close it, and history is append-only. |
| Audit (in this context) | Checking the records against reality, usually for finance or outside auditors. Here that means searching the register (by office, category, state) and taking the Excel or PDF export as the evidence, generated from the same data the screens show. | No separate audit module: audits are served by the R5 search filters (office scopes including descendants, category, status) and the R6 register exports. |
| Domain-Driven Design (DDD) | A way of writing software where the business rules (what it means to retire an asset, what a legal office tree is) live in one clearly marked part of the code, named in the business's own vocabulary, instead of being scattered through screens and database code. | The discipline behind `AssetLite.Domain`: aggregates, value objects, domain events and domain services whose names mirror the requirements (R1-R8), with persistence and transport pushed to outer layers. |
| Clean Architecture | An arrangement where the business rules sit at the center and everything else (database, web) points inward at them, so the core never depends on a tool it does not need. | Domain ← Application (CQRS handlers, ports) ← Infrastructure (EF Core 10 + SQLite) ← API; dependencies point one way and the domain layer has zero package references. |
| CQRS | Short for "command query responsibility segregation": changes (commands) and reads (queries) are written as separate small handlers, each doing one job, instead of one big service doing both. | The Application layer exposes its 20 use cases as `ICommandHandler` / `IQueryHandler` pairs that the API controllers dispatch to. |
| Value object | A small value defined by what it contains rather than by an identity: two "USD 500" amounts are the same money. Being strict about formats (an asset tag, an amount) catches typos at the edge instead of corrupting data later. | Immutable types such as `AssetTag` and `Money` with parse-and-validate rules, persisted through EF Core value converters. |
| Aggregate | A cluster of records the system treats as one unit when changing things. An asset and its whole assignment history are saved or rejected together, so they can never disagree. | The `Asset` aggregate root: assignment history lines and lifecycle transitions share one consistency boundary and persist as a unit. |
| Specification pattern | A tidy way to write a business question as a reusable object, such as "is this asset in stock?", that can be asked of any asset or combined with other questions. | Small predicate objects (`ISpecification<T>`, for example `AssetStatusSpecification`) that compose business criteria inside the domain layer. |
| Aspire orchestration | A conductor for running the app: one command starts the API, the web app, and a dashboard showing logs, traces and health for both. | .NET Aspire 13.5 AppHost hosting the API (`AddProject`) and the Angular dev server (JavaScript-app resource with `WithHttpEndpoint(env: "PORT")` and an `aspire` npm script honoring `$PORT`); see [ADR 0002](adr/0002-aspire-orchestration.md). |
| Angular signals / zoneless | Signals are the framework's way of marking data the screen should react to; "zoneless" means the framework updates the screen straight from those signals, without the older, heavier machinery that watched everything for changes. | All SPA state is signals (HTTP data flows through `toSignal` with explicit loading, error and retry states); `provideZonelessChangeDetection()` removes zone-based change detection. |
| RFC 9457 ProblemDetails | A standard shape for error responses on the web, so any client knows where to look for what went wrong. Here the domain error's code rides inside it, which is why the screen can say exactly why a change was refused. | The machine-readable problem-details format every controller emits for failures: one shared ErrorOr mapping to 400/404/409, with the domain error code as the title. |
