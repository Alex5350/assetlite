# Requirements, design thinking and development process

This document is the "why" behind AssetLite: the user requirements the application was designed
against, the reasoning that turned them into architecture, the challenges that surfaced during
the build, and the commit-by-commit order of work. It exists so a reader can evaluate not just
the code but *how the problem was approached*.

## The problem (user requirements)

IT teams in multi-site organizations lose money to a boring problem: nobody knows exactly which
physical devices exist, where they are, or who has them. Spreadsheets drift from reality within
weeks. The requirements below were written as the product brief for this project:

| # | Requirement |
|---|-------------|
| R1 | Track physical assets - computers, monitors, desktops, laptops, tablets, phones, networking gear, any equipment - with serial numbers, purchase details and condition. |
| R2 | Organize assets under an **office hierarchy**: a central HQ governing regional and site offices, with no cycles and a bounded depth. |
| R3 | Every asset gets a **unique human-readable tag** and a **scannable label** (barcode + QR) that a phone can resolve to the asset's page. |
| R4 | Assets move through a **lifecycle** - in stock, assigned to a person, maintenance, retired, disposed - with history: who had what, when. |
| R5 | **Search fast** across thousands of assets by tag, serial, name or model, filtered by office (including sub-offices), category and status. |
| R6 | Produce **reports** (inventory summaries by office and category) and **export the full asset register to Excel and PDF**. |
| R7 | A web UI an IT admin at HQ and a site manager can both use daily; fast, responsive, no training required. |
| R8 | Cheap to run locally and easy for any developer to clone and start. |

## How the requirements shaped the design

- **R2 → the office hierarchy became a domain concern, not a UI concern.** Cycle prevention,
  depth capping (4 levels) and "cannot move an office under its own descendant" live in the
  domain service `IOfficeHierarchy`, tested independently of persistence. The UI just renders
  the tree and surfaces the domain's error codes.
- **R3 → tags are a value object and labels are generated server-side.** `AssetTag` ("AST-000123")
  is a value object with its own parsing rules; the Code 128 barcode encoder is hand-rolled and
  verified against a computed known-vector (symbols, mod-103 checksum, module count), so label
  generation has zero third-party barcode dependencies; QR codes encode the public asset URL.
- **R4 → the asset lifecycle is a state machine with typed errors.** Every transition
  (`AssignTo`, `ReturnToStock`, `StartMaintenance`, `Retire`, `Dispose`, `TransferTo`) is legal
  only from defined states; illegal attempts return codes like `Asset.CannotAssignRetired` that
  flow unchanged to the UI as readable panels. Assignment history is part of the aggregate.
- **R5 → search is server-side and contract-tested.** The API takes `search`, `officeId` +
  `includeDescendants`, `categoryId`, `status`, paging; the descendant scope resolves to an
  office-id list in the application layer so the database query stays a flat `IN` filter.
- **R6 → exports are generated by the backend** with ClosedXML (Excel) and QuestPDF (PDF), so
  the same files can later be produced by a job, an email or an API client - not just a browser.
- **R7 → Angular 21, signals-first, zoneless.** All state is signals; data flows through
  `toSignal` with explicit loading/error/retry states; templates use the new control flow; the
  whole UI ships with Tailwind v4 utility classes over a small design layer.
- **R8 → SQLite + Aspire orchestration.** Clone, `dotnet run` the AppHost (API + dashboard),
  `npm start` the SPA - 45 seeded assets across 7 offices make every screen real on first load.

## Challenges encountered (and their resolutions)

1. **LINQ vs. value-converted columns** - text search over the `AssetTag` value converter
   couldn't use `string.Contains` in SQL. Resolved with a composable `FromSqlInterpolated`
   predicate (`instr(lower(...))`) while keeping other filters as LINQ.
2. **Aspire's JavaScript-app resource** - orchestrating `ng serve` through Aspire failed at the
   process level (evidence in [ADR 0002](adr/0002-aspire-orchestration.md)). Decision: Aspire
   orchestrates the API; the SPA keeps the standard npm flow. Partial adoption with evidence
   beats a broken one-command story.
3. **Contract drift between SPA and API** - live-testing caught the SPA sending
   `searchText`/`includeDescendantOffices` where the API expects `search`/`includeDescendants`,
   the office tree being a single root object, and registration binding `purchaseCost` - all
   fixed and pinned by tests. Lesson recorded: mirror DTOs from source, verify against the
   running API early.
4. **Two latent SPA bugs found by its own test suite** - forms bound `(ngSubmit)` without
   `FormsModule` (native submits would have reloaded the page) and a success notice cleared
   synchronously before render. Both fixed; the spec files document the regressions they guard.
5. **TypeScript 7 temptation** - GA'd weeks before this build, but Angular's tsgo bridge is
   unshipped; evaluated and deferred with reasons in [ADR 0003](adr/0003-typescript-version.md).
6. **QuestPDF 2026 API changes** - `PageSizes.A4.Landscape()` became a method and column
   syntax changed; the export code follows the current fluent API (not the older docs).
7. **Tailwind silently not compiling** - the frontend shipped `postcss.config.mjs` (the
   config format used by the generic Vite/webpack ecosystem), but the Angular CLI only
   auto-detects `.postcssrc.json`. Symptom: builds inlined raw `tailwindcss/index.css`
   without running the Tailwind transform, so browsers received theme variables wrapped in
   `@theme` at-rules they drop, and zero utility classes - an "unstyled" app that still
   passed every test, because none of the specs assert computed styles. Diagnosis trail:
   the served stylesheet contained `@theme default` blocks and no `.flex`/`.btn` rules.
   Fix: rename the config to `.postcssrc.json`. Lesson recorded: when output looks wrong,
   inspect the bytes the client actually receives before blaming the client - and a
   styling smoke check belongs in the verification loop, not only component specs.

## Development process (commit order)

| Phase | Commits |
|-------|---------|
| 1. Repository | `chore: initialize repository with build configuration` |
| 2. Domain | value objects, ids, enums, error catalog → Office + Category → Asset aggregate + events → ports/CQRS mapping → 19 use cases |
| 3. Infrastructure | EF persistence → repositories/allocator/UoW/time → migration → barcode + QR labels → Excel/PDF exports → wiring + demo seed |
| 4. API + Aspire | controllers (ADR 0001) → ServiceDefaults + AppHost |
| 5. SPA | Angular 21 + Tailwind scaffold → models/API/shared UI → dashboard + asset list → contract alignment fix → asset detail + labels → register form → offices → categories → reports |
| 6. Tests | 197 domain → 84 application → 42 API integration → 46 frontend (+ the two bug fixes they forced) |
| 7. Orchestration + docs | Aspire scope finalized (ADR 0002) → ADRs 0003/0004 + CI → README + this document |

Every commit builds; Conventional Commits carry the *why* in their bodies. All ADRs live in
[adr/](adr/).
